wake CLI ​

wake connects a repository's plan to a Wake project, keeps it in sync and connects your coding agents. wake help <command> prints any command's options; wake --version prints the version.

A usage error exits 2; any other failure exits 1 with one wake: ... line. The CLI never prints a token.

Which server a command uses ​

wake sync, watch, doctor, evidence and the agents' hooks use the server the repository's .wake/config.json names. The commands that connect a repository choose one:

  • wake login and wake setup --agent use --server, then WAKE_SERVER, then the server the installer recorded on this machine, then the address a local installation serves by default (see Your Wake URL).
  • The guided wake setup uses --server, then the repository's server, the recorded one, the only server you are logged in to, then WAKE_SERVER; else it asks.
  • wake init uses the stored login that matches --server and --workspace.

So on the machine where you installed Wake, plain wake login finds your Wake URL. On any other machine, run wake login --server <your Wake URL> once. The address must use https; plain http is allowed only for localhost, 127.0.0.1 and [::1].

setup ​

sh
wake setup [--agent <agent>] [--server <url>] [--workspace <id>] [--project <id>] [--name <name>] [--no-browser]

Connects this repository and a coding agent in one command; it never commits. Without --agent, the choices are made in the browser: the server, the project and the agent. With --agent (claude-code, opencode, pi or codex), only the login is asked. Running it again changes nothing that is already set up, and resumes where a failed step stopped. See Your first project.

login ​

sh
wake login [--server <url>] [--workspace <id>] [--no-browser]
wake login [--server <url>] --with-token

Signs the CLI in and stores a personal access token of one workspace in the OS keychain, or in a file readable only by you when there is no keychain. In a terminal it signs in with the browser; --with-token, or a token piped on standard input, reads a token instead. See Install the CLI and sign in.

init ​

sh
wake init [--server <url>] [--workspace <id>] [--project <id>] [--name <name>] [--default-branch <name>] [--plan <method>] [--no-sync]

Connects the repository to a Wake project, creating it when it does not exist, writes .wake/config.json (commit it) and syncs the plan. --plan is openspec, spec-kit or odd; by default it is detected. --no-sync connects without syncing.

sync ​

sh
wake sync [--allow-empty]

Reads the plan, writes a stable wake: id on each task that needs one (OpenSpec only; Wake writes nothing into Spec Kit or ODD files) and sends the plan this branch owns: the default branch's is committed, other branches' are provisional. It also sends the repository's version tags. Nothing is written or sent when a file has errors; each is printed as path:line: message.

Before what the server changed, it may print two notes; neither stops the sync:

text
2 tasks had text longer than Wake keeps and were shortened; run `wake doctor` to list them.
3 open tasks have no "Done when:" line, so Wake cannot show when they are done; run `wake doctor` to list them.

The second counts open checkbox tasks without a Done when: line (done tasks and ODD table rows never count); add one under each task so its detail says when it is finished. wake watch, wake init and wake setup print the same notes.

On the default branch, a plan with no committed work would remove every committed phase from Wake; the server refuses it unless --allow-empty confirms it. See OpenSpec, Spec Kit, ODD and Milestones and task text.

watch ​

sh
wake watch

Syncs now, then again 300 ms after the last change to the plan, the git branch or a tag. Failed syncs are retried after 1 s, 2 s, 4 s and so on, up to 60 s. Stop it with Ctrl-C.

connect and disconnect ​

sh
wake connect <agent>
wake disconnect <agent>

connect installs or updates an agent's Wake adapter in this repository: Wake's MCP server, the hooks that run wake hook, and the agent's skills and commands. It merges into existing configuration and never writes a token; commit the files. disconnect removes what connect added, keeping files you edited. See Agents and plans.

doctor ​

sh
wake doctor [--agent <agent>]

Checks, changing nothing: the repository's .wake/config.json, its plan method and files, the plan's text, the open tasks without a Done when: line (up to 20 listed as path:line), a login that can read its project, the server's version against the CLI's, the MCP endpoint, wake on PATH, and each connected agent's files. Each line starts with ✓, ✗ or ! (a warning), and a failure ends with its fix. It exits 0 when every check passes or only warns, and 1 when one fails. See Troubleshooting.

evidence ​

sh
wake evidence <file> --task <id> --session <id> [--title <text>] [--kind <kind>]

Attaches a file as evidence of a task, acting as the claim your user holds on it with that session. Images (.png, .jpg, .jpeg, .webp, .gif) and text (.txt, .log), at most 10 MiB; - reads text from standard input. --kind is screenshot, test_report, log, link, note or other; --title takes up to 200 characters. Your agent usually runs it.

upgrade ​

sh
wake upgrade [--version <x.y.z>] [--check] [--no-server]

wake upgrade installs the version the server of the current repository recommends, or the newest release outside a connected repository (the newest prerelease for a prerelease CLI). It downloads that release's wake-cli.tgz, install.sh, SHA256SUMS and SHA256SUMS.sig, verifies the signature with the release key built into the CLI and both files against SHA256SUMS (no ssh-keygen needed), checks that install.sh carries the version asked for, so an older release's signed files served under a newer tag are refused, and installs the verified file. A release that is not signed, does not verify or has no wake-cli.tgz installs nothing.

Installed withwake upgrade runs or prints
npm install --globalnpm install --global <the verified wake-cli.tgz>
pnpm add --globalpnpm add --global <the verified wake-cli.tgz>, from a copy kept in wake/cli/ of the configuration directory
npxprints npx --yes --package https://github.com/dalodev/wake-dist/releases/download/v<version>/wake-cli.tgz wake; installs nothing
  • wake upgrade --check only says whether a newer CLI exists.
  • wake upgrade --version 1.2.0 installs that CLI version, even an older one.
  • A CLI newer than its server installs nothing and prints the wake upgrade --version command that matches the server.

On the machine that hosts Wake (the directory in WAKE_SERVER_DIR, else the one the installer recorded, else the default installation directory), wake upgrade first runs wake-server upgrade there, which upgrades the server and the web app, then upgrades the CLI. If the server upgrade fails, the CLI is still upgraded and the command exits 1. --no-server skips the server, and --version and --check act on the CLI only and never touch it. A remote server is upgraded by whoever runs it.

Automatic upgrade ​

When the server of the repository recommends a newer CLI, the next agent session start runs wake upgrade --version <recommended> in the background and tells the agent. Since it passes --version, it never upgrades a server. It runs only:

  • for a CLI installed with npm install --global or pnpm add --global, never under npx;
  • when CI is not set and WAKE_AUTO_UPGRADE is not off;
  • at most once a day for the same version, so a failing install does not run at every session.

Its output goes to auto-upgrade.log in Wake's configuration directory (~/.config/wake/auto-upgrade.log, or under XDG_CONFIG_HOME).

hook ​

sh
wake hook <session-start|session-end|tool-use> --agent <agent>

Runs from the hooks wake connect installs; you do not run it yourself. session-start syncs and prints the session's context, session-end releases the session's claims, and tool-use reports each tool's name (never its arguments or output) and the new commits. It always exits 0: when Wake is offline or you are not logged in, it prints one Wake: line instead.

Environment ​

VariablePurpose
WAKE_SERVERThe server wake login and wake setup --agent use without --server (see Which server a command uses); the only one WAKE_TOKEN is sent to
WAKE_TOKENA personal access token to use instead of a stored login, for CI; see In CI
WAKE_CREDENTIALSfile stores the login in a file instead of the OS keychain
WAKE_AUTO_UPGRADEoff keeps the agent session start from upgrading the CLI
WAKE_ADAPTER_UPDATESoff keeps the agent session start from updating the adapter's files; it then says to run wake connect <agent>
WAKE_NO_UPDATE_CHECK1 stops the daily check that suggests wake upgrade; it is off when CI is set
WAKE_SERVER_DIRThe local installation's directory, for wake upgrade (default: the one the installer recorded, else the default installation directory)
CIAny value turns off the automatic upgrade and the daily update check
