Back up and restore ​

Back up ​

sh
wake-server backup

It writes one file, backups/wake-<version>-<UTC time>.tar in the installation's directory (directory mode 0700, file mode 0600), and prints one line with its path and size:

text
Backup written: /home/you/wake-server/backups/wake-2.4.0-20261102T215053Z.tar (589 MiB)

Wake keeps serving while it runs. Every upgrade and every restore writes a backup first.

Free disk first ​

Before a backup writes anything, wake-server checks the disk that holds backups/: it needs about the database's size plus twice the evidence files' size free, for the copy and its file. With less, the backup, an upgrade (including the daily one) or a restore stops before it changes anything, and Wake keeps running:

text
wake-server: not enough free disk for the backup: it needs about 300 MB in /home/you/wake-server/backups, 200 MB are free

Free space on that disk, for example by copying older backups elsewhere and deleting them from backups/, then run the command again. When a size cannot be read, the backup runs without the check.

Copy backups off the machine. A healthy upgrade removes the older upgrade backups (see Upgrade backups kept); wake-server never deletes any other backup, so remove the ones you no longer need yourself.

Back up on a schedule ​

Wake takes no backup by itself other than the one before each upgrade. To take one every night, run crontab -e as the user who installed Wake and add a line such as this one, which backs up at 03:30, machine time, and appends the output to a log. Write your installation directory in place of /home/you/wake-server:

text
30 3 * * * PATH=/usr/local/bin:/usr/bin:/bin /home/you/wake-server/wake-server backup >>/home/you/wake-server/backup.log 2>&1

PATH lets cron find docker; if command -v docker names another directory, add it. Then copy the new backups off the machine, for example with your usual backup tool or rsync.

A backup holds:

MemberContents
manifestThe backup's format, the Wake version it was taken from, its time and what wrote it: trigger=upgrade, backup or restore
postgres.sql.gzThe database: accounts, workspaces, tokens and every project's events
evidence/Every evidence file
envA copy of .env, with the installation's secrets: keep backups as private as .env

Restore ​

A restore replaces the database and the evidence files with the backup's. Name the backup by its full path, or by a path relative to the directory you are in:

sh
wake-server restore <your installation directory>/backups/wake-2.4.0-20261102T215053Z.tar

It stops Wake, writes a backup of the current data, replaces the database and the evidence files with the backup's, starts Wake and prints Restored <backup> (Wake <version>). The data it replaced is in <new backup>. Restoring that new backup undoes the restore.

It keeps .env, so the installation keeps its address and secrets, and the backup's accounts sign in.

A backup from a newer Wake is refused, naming the wake-server upgrade --version to run first: the server migrates an older database forward on start, but an older server cannot run a newer one. A missing file, one that is not a Wake backup (a backup compressed again, such as a .tar.gz: decompress it first) or one whose database dump is damaged is refused with nothing changed. A backup keeps working under another name.

wake-server restore also reads a database dump named wake-<version>-<UTC time>.sql.gz, which holds the database only: it restores the database and keeps the evidence files.

Move to another machine ​

Install the same release or a newer one on the new machine, copy the backup into its backups/ and restore it there. The backup's env member holds the old installation's settings: carry over by hand the ones you set yourself, such as sign-in providers, into the new .env.

To move a deployment you run yourself onto an installation, see Run the images yourself.
