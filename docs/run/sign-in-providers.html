Sign-in providers ​

Besides email and password, people can sign in with GitHub, Google, Microsoft and one OpenID Connect provider (Okta, Keycloak, Auth0, Authentik and others). Each provider is off until you set all of its variables; a partial group stops the server at start, naming the missing variables. The web app shows a button for each provider that is on, and never learns a client id, secret or issuer.

Turn one on ​

  1. Register Wake with the provider as a web application, with the callback URL <PUBLIC_URL>/v1/auth/<provider>/callback, where <PUBLIC_URL> is your Wake URL and <provider> is github, google, microsoft or oidc. For https://wake.example.com, Google's is https://wake.example.com/v1/auth/google/callback.

  2. Add the provider's lines to the installation's .env, keeping its mode 0600. A value with $ or spaces goes in single quotes:

    sh
    GOOGLE_CLIENT_ID=...
GOOGLE_CLIENT_SECRET=...

  3. Run wake-server start, which recreates the server with them. Upgrades keep .env.

In local mode your Wake URL is on localhost, so a provider sends the browser back to the machine that runs Wake: provider sign-in works only in a browser on that machine. To sign in with a provider from other machines, install on a domain.

A server you run yourself takes the same variables in its environment; see Server environment.

How accounts are matched ​

Wake identifies an account by the provider's own account id, never by its email. The first sign-in with a provider account creates a user with a personal workspace, and only when the provider reports the email as verified. An email that already belongs to a Wake user is never linked automatically: that person signs in the way they already do and links the provider from Account (Sign-in methods).

Every provider's sign-in uses PKCE (S256): a code intercepted on its way back cannot be redeemed without the verifier the server keeps in the sign-in's HttpOnly cookie. It needs no setting.

Sign-in providers follow who can sign up: on a server open only to invitations, a new account through a provider needs an invitation too, and every new account counts against the free plan's people.

GitHub ​

  1. In GitHub, open Settings → Developer settings → OAuth Apps and choose New OAuth App.
  2. Set Authorization callback URL to <PUBLIC_URL>/v1/auth/github/callback.
  3. Generate a client secret, then set GITHUB_CLIENT_ID and GITHUB_CLIENT_SECRET.

Wake asks for the read:user and user:email scopes and uses the account's primary email, only when GitHub reports it verified.

Google ​

Google sign-in accepts Gmail and Google Workspace accounts.

  1. In the Google Cloud console, configure the OAuth consent screen, then create an OAuth client ID of type Web application.
  2. Add <PUBLIC_URL>/v1/auth/google/callback under Authorized redirect URIs.
  3. Set GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET to the client's id and secret.

Wake asks for the openid, email and profile scopes and trusts Google's email_verified claim.

Microsoft ​

Microsoft sign-in accepts work or school accounts (Microsoft Entra ID) from any organization and personal Microsoft accounts, through the multi-tenant issuer https://login.microsoftonline.com/common/v2.0.

  1. In the Microsoft Entra admin center, open App registrations and choose New registration.
  2. Under Supported account types, choose Accounts in any organizational directory and personal Microsoft accounts.
  3. Add a Web redirect URI <PUBLIC_URL>/v1/auth/microsoft/callback.
  4. Under Certificates & secrets, create a client secret.
  5. Under Token configuration, choose Add optional claim, token type ID, and add email and xms_edov.
  6. Set MICROSOFT_CLIENT_ID to the Application (client) ID and MICROSOFT_CLIENT_SECRET to the secret's value. The secret expires; create a new one before it does.

A tenant administrator can set a work account's email claim to any address, so Wake counts it as verified only for personal accounts or when the xms_edov claim states that the domain owner verified it. Without the optional claim, a work account cannot create a Wake user (provider_email_unverified): that person signs up with a password or another provider and links Microsoft from Account.

OpenID Connect ​

One more provider that speaks OpenID Connect can sign people in, under a name you choose.

  1. In your identity provider, create a confidential web application (client) that uses the authorization code flow, with the redirect URI <PUBLIC_URL>/v1/auth/oidc/callback and the openid, email and profile scopes.
  2. Set OIDC_ISSUER to its issuer URL, the one whose /.well-known/openid-configuration document Wake reads (for example https://sso.example.com/realms/wake for a Keycloak realm), and OIDC_CLIENT_ID and OIDC_CLIENT_SECRET to the client's credentials.
  3. Set OIDC_NAME to the text of its button, for example Acme SSO: 1 to 40 characters.

OIDC_ISSUER must use https (http only on localhost), without a query or fragment. The provider must sign ID tokens with keys published at its jwks_uri and report verified emails with email_verified. Wake uses PKCE (S256) and a nonce, and checks the ID token's signature, issuer, audience, expiry and nonce.

Errors people can meet ​

When a provider sign-in fails, the browser goes back to the screen it started from, which says what happened; starting the sign-in again is safe. Each message and what to do about it are in Troubleshooting.
