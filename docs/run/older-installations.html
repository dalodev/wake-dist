Older installations ​

Most installations need nothing from this page. If yours is older than one of these releases, do what its entry says; the entries are oldest first.

Older than v1.3.0

A repository connected to Claude Code before Wake had its plugin still has Wake's hooks in .claude/settings.json. Its session start says to run wake connect claude-code once, which removes them. Upgrade the CLI first: an older CLI copies the hooks back next to the plugin's, so they would run twice.

Made with v1.3.0 or v1.3.1

An installation made with v1.3 has a wake-server that downloads releases from a repository that is no longer public, so it cannot upgrade. Replace it once with the current one, then upgrade; your data and secrets are kept:

sh
cd <your installation directory>
curl -fsSL https://github.com/dalodev/wake-dist/releases/latest/download/install.sh -o wake-server
chmod 700 wake-server
./wake-server upgrade

A project connected to Claude Code by Wake 1.3 names that old repository as its plugin marketplace. Its next session start moves the entry to wake-dist and asks you to commit .claude/settings.json: commit it.

Older than v1.10.1

wake-server start does not exist yet. Start Docker, then run wake-server upgrade, which brings it. To start Wake without upgrading, run docker compose up -d in <your installation directory>.

Older than v2.2.0

Your next upgrade still runs the wake-server you have, which checks the release's checksums but not their signature, does not pause Wake for the backup, and rolls back without restoring the database. Before it:

  1. Run wake-server backup.
  2. When verifying the release matters to you, check its files by hand as in Verify a download, then run wake-server upgrade --version v2.2.0. Every upgrade after it verifies signatures.
  3. After the upgrade, run wake-server start once. It gives the server its own storage user, adding two lines to .env, recreating the services and printing The server now uses its own storage user, wake-server. When they do not become healthy, it puts .env back as it was, starts them again with the storage's root keys, and exits 1.

Backups written before v2.2 are backups/wake-<version>-<UTC time>.sql.gz and hold the database only. wake-server restore reads them: it restores the database and keeps the evidence files. Upgrades never remove them; delete them by hand when you no longer need them.

Older than v2.3.0

The daily upgrade's crontab line appends to auto-upgrade.log without ever rotating it. It still counts as on. After upgrading, run wake-server auto-upgrade on once to rewrite the line in place; your other crontab lines stay as they are. The next wake-server upgrade rewrites it too.

The upgrade also brings the limits on the services' container logs. The first cleanup pass after it deletes the whole backlog of expired records and can take a while; its records cleaned log line says how long.

Older than v2.4.0

The upgrade to v2.4.0 still runs the wake-server you have, which keeps every upgrade backup and writes no LICENSE. Run wake-server upgrade once more afterwards: it finds nothing to upgrade and writes the release's LICENSE. The upgrades after it remove older upgrade backups.

Backups written before v2.4 do not record what wrote them, so upgrades never remove them. Delete them by hand from backups/ when you no longer need them.

A wake CLI older than v2.4.0 looks for the server only in WAKE_SERVER_DIR and the default directory. When you installed with --dir, run wake-server upgrade there yourself, or set WAKE_SERVER_DIR before wake upgrade.
