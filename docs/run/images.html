Run the images yourself ​

The installer is the simplest way to run Wake. To run it on your own platform instead, such as Kubernetes, an external Postgres or your own proxy, run the two published images.

The images ​

ImageRunsPort
ghcr.io/dalodev/wake-server:<version>The API server, MCP at /mcp, OAuth and event streams3000
ghcr.io/dalodev/wake-web:<version>The web app as static files served by Caddy, forwarding /v1 to the server so cookies stay on one origin5173

<version> is the release without the v, such as 2.4.0. latest follows the newest release; prereleases such as 2.4.0-rc.1 never move it. Pin an exact version in production. A release's compose.yaml names both images by digest too, ghcr.io/dalodev/wake-server:<version>@sha256:..., the digest the release signed: Docker runs that image even if the tag is pushed again.

Both images run as a user other than root, with a read-only root file system, no capabilities and no-new-privileges (the web image needs a writable /tmp). They hold only what they run.

Both carry the license they ship under, at /usr/share/licenses/wake/LICENSE, and the label org.opencontainers.image.licenses, set to LicenseRef-Wake-Free-License:

sh
docker run --rm --entrypoint cat ghcr.io/dalodev/wake-server:2.4.0 /usr/share/licenses/wake/LICENSE
docker image inspect --format '{{index .Config.Labels "org.opencontainers.image.licenses"}}' ghcr.io/dalodev/wake-server:2.4.0

Layout ​

Put both containers behind a TLS reverse proxy that you control:

  • https://wake.example.com → the web container. Browsers use this origin; the web container forwards /v1 to the server.
  • https://api.wake.example.com → the server container. The CLI, coding agents (MCP and OAuth) and evidence downloads use this origin. It is the server's PUBLIC_URL.
  • Postgres 18, reachable only from the server.
  • An S3 bucket (S3, R2 or MinIO) that agents reach for uploads and browsers for downloads, through presigned addresses; see Evidence storage.

For this layout, the server gets:

sh
DATABASE_URL=postgres://wake:<password>@db.internal:5432/wake
PUBLIC_URL=https://api.wake.example.com
WEB_ORIGINS=https://wake.example.com
WEB_APP_URL=https://wake.example.com
TRUST_PROXY=true
EVIDENCE_S3_ENDPOINT=https://<account>.r2.cloudflarestorage.com
EVIDENCE_S3_BUCKET=wake-evidence
EVIDENCE_S3_ACCESS_KEY_ID=<key id>
EVIDENCE_S3_SECRET_ACCESS_KEY=<secret>
EVIDENCE_S3_REGION=auto

Every variable, and the web container's two, are in Server environment. Keep secrets in your platform's secret store, never in an image or a committed file.

Run the containers ​

This example runs both containers on one host with Docker; any container platform works the same way:

sh
docker network create wake
hardened="--read-only --cap-drop ALL --security-opt no-new-privileges"
docker run -d --name wake-server --network wake $hardened --env-file /etc/wake/server.env \
  -p 127.0.0.1:3000:3000 ghcr.io/dalodev/wake-server:2.4.0
docker run -d --name wake-web --network wake $hardened --tmpfs /tmp \
  -e WAKE_API_PROXY=http://wake-server:3000 \
  -e WAKE_S3_URL=https://<account>.r2.cloudflarestorage.com \
  -p 127.0.0.1:5173:5173 ghcr.io/dalodev/wake-web:2.4.0
curl -f http://127.0.0.1:3000/health

$hardened is unquoted on purpose, so the shell splits it into its options. Your TLS proxy should add Strict-Transport-Security to both origins.

Every server response carries X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer, X-Frame-Options: DENY and a Content-Security-Policy. The web container's policy allows images from the origin of its WAKE_S3_URL, so evidence images load from the storage. The web container answers any Host; your proxy decides which names reach it.

Migrations ​

The server applies pending database migrations when it starts (MIGRATE_ON_START=true). A Postgres advisory lock serializes them, so several replicas can start at once; only one migrates. Migrations only add to the schema. To migrate as a separate step, run one server with MIGRATE_ON_START=true first and the others with false.

Upgrade order ​

  1. Back up Postgres.
  2. Deploy the new server image (it migrates on start) and the new web image together: a newer server can send kinds of activity an older web app cannot read.
  3. Ask everyone to update their wake CLI. A newer CLI may send fields an older server refuses, while a newer server accepts every older CLI.

On an installation, wake-server upgrade does steps 1 and 2. wake upgrade on the machine that runs the installation does them too, then upgrades that machine's CLI; CLIs installed globally on other machines follow by themselves at their next agent session. See Which command to run.

Move onto an installation ​

The installer does not adopt a deployment you run yourself. To move one onto it, copy the database into a new installation:

  1. Upgrade the existing deployment to the release you will install, or note its version: the installation must run the same release or a newer one.

  2. Stop the existing server, so nothing writes during the copy, and dump its database without owners, since the installation's database user is wake. Use a pg_dump of the same major version as the Postgres it reads, or newer:

    sh
    pg_dump "$DATABASE_URL" --no-owner --no-privileges -Z 6 -f wake-move.sql.gz

  3. Install Wake on the new machine or directory, and do not create an account in it yet.

  4. Copy wake-move.sql.gz into the installation's backups/, named with the version the deployment runs and a UTC time, such as wake-2.4.0-20261024T101500Z.sql.gz, and restore it with wake-server restore (see Back up and restore).

  5. Copy the evidence files: the objects of your old bucket go into the installation's wake-evidence bucket in MinIO (an S3 client such as MinIO's mc mirror does it). Evidence whose file is missing cannot be opened; everything else works without it.

  6. Point the clients at the new address. The installation serves the app and the API on one origin, where your layout may have used two. In each connected repository, set server in .wake/config.json to the new address, run wake login --server with it and wake connect <agent> (it rewrites the MCP address), commit, and sign the agent in again.

The installation starts with no sign-in provider and no external storage, so accounts that only sign in with a provider cannot sign in until you turn that provider on (Sign-in providers).
