Upgrade ​

Wake has two parts, and both upgrade: the server, with the API and the web app, on the machine that runs Wake, and the wake CLI, on every machine where you or your agents work. Upgrade the server first; the CLIs follow it.

Which command to run ​

The command depends on the machine you are on:

Where you areRunWhat it upgrades
On the server's machinewake upgradeThe server and the web app first, then the CLI to the server's new version
On the server's machine, server onlywake-server upgradeThe server and the web app
On any other machinewake upgradeThe CLI, to the version your server recommends
Anywhere, to look without changing anythingwake upgrade --checkNothing: it prints whether a newer CLI exists

wake-server upgrade moves to the newest stable release, skipping prereleases. You rarely need to run these commands by hand, because both parts also upgrade by themselves.

What upgrades by itself ​

The server upgrades once a day, and each CLI upgrades at its next agent session once its server has moved. So the server goes first and the CLIs follow by themselves.

Upgrade on a schedule ​

A new installation upgrades its server every day at 04:17, in the machine's local time, unless it was installed with --no-auto-upgrade. Turn it on or off, or see which it is, with:

sh
wake-server auto-upgrade on
wake-server auto-upgrade off
wake-server auto-upgrade status

on adds one line to your crontab that runs wake-server upgrade, with the PATH you ran it with (cron's own often lacks docker). It needs crontab. Each run is an ordinary server upgrade: backup first, rollback when the new version is not healthy, nothing changed when already current.

Each run logs to auto-upgrade.log in <your installation directory>. When the log grows past 1 MiB, it moves to auto-upgrade.log.1, replacing the previous one, so it never takes more than about 2 MiB.

The daily upgrade never touches the CLI. Turn it off when an unattended restart of the server would disturb your team, and upgrade by hand instead.

The CLI at its next session ​

When an agent session starts in a connected repository and the server recommends a newer CLI, the CLI upgrades itself in the background, and the session says the wake CLI 2.4.0 is upgrading to 2.4.1 in the background. It does this only when:

  • the CLI was installed globally, with npm install --global or the package manager you installed it with (not when it runs through npx);
  • the CI environment variable is empty;
  • WAKE_AUTO_UPGRADE is not off.

It tries each version at most once a day, so a failing install does not run at every session. Its output goes to ~/.config/wake/auto-upgrade.log (under XDG_CONFIG_HOME when you set it). It never upgrades a server.

Claude Code's wake plugin updates itself from Wake's marketplace; there is nothing to run.

Why the server goes first ​

A newer CLI may send fields an older server refuses, while a newer server accepts every older CLI. That is why wake upgrade on the server's machine upgrades the server before the CLI, and why the other CLIs wait for the server to recommend their new version.

When the CLI is newer than its server, wake upgrade installs nothing and prints wake 2.5.0 is newer than this server (2.4.0); `wake upgrade --version 2.4.0` installs the server's version. Upgrade the server, or install the server's version as it says.

What a server upgrade does ​

wake-server upgrade upgrades the server and the web app together, since the web app ships with the server. It runs these steps:

  1. Downloads the new release's files and their signed checksums, verifies the signature with the release key your installation already has (a new release cannot bring its own key), then each file against the checksums. A missing release, a missing or wrong signature, or a mismatch stops it with nothing changed and no backup.
  2. Stops the server and the web app, so nothing writes after the backup, and writes a backup to backups/ (see Back up and restore). When the backup fails, it starts them again and stops with nothing changed: the old version keeps running.
  3. Replaces the installation's files, LICENSE included, and sets the new version in .env, keeping your settings and secrets. It pulls the new images and starts them; the server applies new database migrations as it starts.
  4. Waits up to two minutes for every service to be healthy and, on an installation without --domain, up to two more for <your Wake URL>/health to answer. Then it prints Upgraded Wake 2.3.0 → 2.4.0. Backup: <file>.
  5. Removes the older upgrade backups, keeping the one it just wrote (see Upgrade backups kept), and prints how many it removed and the space they used, such as Removed 1 older upgrade backup, 589 MiB.

When the new version is not healthy in time, the upgrade rolls back: it puts back the previous files and version, restores the database from the upgrade's backup (the new server may have migrated it), starts the previous version, and exits 1 saying it rolled back. Evidence files stay as they are. When the restore or the start fails, it exits 1 naming wake-server restore <backup>, which finishes the job.

An installation that already runs the newest release prints that it is up to date and changes nothing, except that it writes the installed release's LICENSE when the installation has none.

Downgrades are refused: a version lower than the installed one exits 1, because migrations only move forward. To go back, restore a backup. One upgrade, backup or restore runs at a time per installation; a second one exits 1, and a lock left by a killed command does not block the next one.

What a CLI upgrade does ​

wake upgrade installs the version your server recommends, which is always the server's own version. Outside a connected repository, it installs the newest release instead. Before it installs anything, it checks the release's signed checksums with the Wake release key; a release that is not signed or does not verify installs nothing.

It installs with the package manager that installed the CLI, such as npm install --global for a global npm install. When the CLI runs through npx, which installs nothing, it prints the npx command to run instead. See also Update the CLI.

Upgrade to a specific version ​

Name the version to install one release instead of the newest. Prereleases are included:

sh
wake-server upgrade --version v2.4.0
wake upgrade --version 2.4.0

wake-server upgrade --version refuses a version lower than the installed one. wake upgrade --version installs that CLI version even when it is older, and never touches the server; wake upgrade --check does not either.

Upgrade backups kept ​

Each upgrade's backup is a full copy of the database and the evidence files, so a healthy upgrade keeps only the newest upgrade backup, the one it just wrote, and removes the older ones.

To keep more, set WAKE_UPGRADE_BACKUPS in the installation's .env to a whole number from 1 to 100, for example:

sh
WAKE_UPGRADE_BACKUPS=3

The backup just written counts as one, and the others are ordered by the time they record. A missing or empty value means 1. Any other value keeps every backup, and the upgrade still runs and prints:

text
! WAKE_UPGRADE_BACKUPS in .env must be a whole number from 1 to 100: every backup was kept

An upgrade never removes backups written by wake-server backup or wake-server restore, nor any other file in backups/. An upgrade that fails, rolls back or finds nothing to upgrade removes nothing. A backup it cannot remove prints ! could not remove <file>, and the upgrade still succeeds.

How you hear of a new release ​

Wake tells you about a new release in three places.

The web app. Every Wake server asks GitHub for the newest stable release when it starts and every 12 hours, with a 5-second timeout. It sends nothing but a User-Agent: wake-server/<version> header, and a failed check never delays start-up or a request. When a newer release exists, signed-in people see a banner, such as Wake 2.4.1 is available. This server runs 2.4.0., with links to the release notes and the upgrade guide. Dismiss hides it until the next release.

wake-server status. It asks GitHub for the newest release itself and prints Wake 2.4.1 is available: run <your installation directory>/wake-server upgrade, whatever the server's setting.

The CLI. After commands such as wake login, wake sync and wake watch, and when an agent session starts, the CLI prints one line when it is behind its server, such as wake: wake 2.4.1 is available for this server (you have 2.4.0); run `wake upgrade`. It reads its server's version at most once an hour. It also reads GitHub's releases, at most once a day and never in CI, and names the newest one when its server recommends no version.

To turn the server's check off, add this line to the installation's .env, then run wake-server start, which recreates the server with it; upgrades keep the line:

sh
WAKE_UPDATE_CHECK=off

No request then goes to GitHub, and the banner never shows. A server you run from the images yourself takes UPDATE_CHECK=off in its environment instead; see Server environment.

To turn the CLI's release check off, set WAKE_NO_UPDATE_CHECK=1. The line that compares the CLI with its server still shows.

When the server is somewhere else ​

wake upgrade looks for the server's wake-server in this order:

  1. The directory in WAKE_SERVER_DIR, when you set it. When that directory holds no executable wake-server, the command says so and exits 1, after upgrading the CLI.
  2. The directory the installer recorded, so an installation made with --dir is found.
  3. The default directory.

When none holds an installation, wake upgrade upgrades the CLI only. wake upgrade --no-server skips the server even when it finds one. When the server upgrade fails, the CLI is still upgraded and the command exits 1.

A server on another machine is upgraded by whoever runs it, on that machine. A server you run from the images yourself follows Run the images yourself.

Older installations ​

An installation older than v2.4 may need one step by hand before or after its next upgrade: see Older installations.
