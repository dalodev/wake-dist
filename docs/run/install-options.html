On this page

Install options ​

Install Wake installs the whole stack on one Linux, macOS or Windows (WSL 2) machine with one command. This page covers what it needs, its options, serving Wake on a domain and what it writes.

What you need ​

  • Linux, macOS, or Windows with WSL 2 (inside a distribution), with Docker Engine or Docker Desktop running, and the Docker Compose v2 plugin (docker compose version).
  • curl, and sha256sum or shasum.
  • ssh-keygen from OpenSSH 8.1 or newer, which verifies the release signature: macOS ships it; on Linux it is the openssh-client package. Without it the installer, wake-server upgrade and wake-server install-cli stop with one line naming the package.
  • For a domain: a machine reachable from the internet on ports 80 and 443.

Before it writes anything, the installer checks the tools, the directory and the ports, and stops with one line naming what is missing. A domain's DNS and firewall can only be checked once Wake runs: see Install on a domain. The images are public: no GitHub account, gh or docker login is needed.

Every release is signed. The installer, wake-server and wake upgrade use a downloaded file only when the release's signature verifies with the key they carry and the file matches the release's checksums. To check the installer itself before running it, see Verify a download.

Options ​

Options go after sh -s -- when you pipe the script, or after sh install.sh:

OptionDefaultPurpose
--dir DIR$HOME/wake-serverInstallation directory. For a new installation it must be empty or missing; running again on an existing one is safe (see Run it again)
--port PORT8080Local mode: the app's port on 127.0.0.1
--s3-port PORT8081Local mode: evidence storage's port on 127.0.0.1
--domain HOSTServe https://HOST instead (see Install on a domain)
--no-auto-upgradeLeave daily upgrades off (later: wake-server auto-upgrade on)
--no-cliDo not install the wake CLI (later: wake-server install-cli)
--no-browserDo not open the browser at the end
--cli-onlyInstall only the wake CLI of the release, on a machine that does not run the server: see Install the CLI. Takes no other option
-h, --helpShow the options

For example:

sh
curl -fsSL https://github.com/dalodev/wake-dist/releases/latest/download/install.sh | sh -s -- --dir /srv/wake --port 8300 --s3-port 8301

A busy port stops the installer with a line naming the port and the option to change it. An invalid option exits 2 and writes nothing.

In local mode Wake listens on 127.0.0.1 only. The app, the API, OAuth and MCP share one address, http://localhost:<port> (8080 unless you passed --port), and evidence files go to http://localhost:<s3-port> (8081 unless you passed --s3-port).

What else the installer sets up ​

Once the stack is healthy, the installer:

  • Turns on daily upgrades, as wake-server auto-upgrade on does (see Upgrade on a schedule), unless --no-auto-upgrade is given. Without crontab it prints a ! line and goes on.
  • Puts wake-server on your PATH: a small script in $HOME/.local/bin (WAKE_BIN_DIR changes the directory) that runs the installation's wake-server, marked # Managed by the Wake installer. It never replaces a file there that is not its own. When that directory is not on PATH, the output gives the export PATH=... line to add to your shell profile.
  • Installs the wake CLI of the same release when Node.js 24 or newer and npm are present: it downloads wake-cli.tgz, verifies it like the other files and runs npm install --global on it. Without Node it says so; install Node, then run wake-server install-cli. A file that does not verify is not installed. When npm fails, the output shows npm's last lines and the command to retry.
  • Opens the browser on the sign-up page with open (macOS) or xdg-open (Linux, with a display); WAKE_OPEN_COMMAND names another program, and --no-browser skips it. Without one, the output names the address to open.
  • Records the installation for the CLI in ~/.config/wake/server.json (or under XDG_CONFIG_HOME): its address and directory, so wake setup finds it.

A step it could not do shows ! with the reason and the command that does it later; the install still exits 0. The installer never touches a repository.

One machine keeps one Wake server: when another installation exists in another directory, the installer exits 1 and names it. Run the installer with --dir set to that directory, or remove that installation first.

Install on a domain ​

To serve Wake on https://wake.example.com with a certificate:

  1. Create DNS records (A, and AAAA for IPv6) for both wake.example.com and s3.wake.example.com, pointing at the machine. Evidence storage needs its own name: the presigned upload and download addresses sign the host.

  2. Open ports 80 and 443 in the firewall, and keep them free: Caddy listens on both, and obtains and renews the certificates for both names through them.

  3. Run the installer with the domain:

    sh
    curl -fsSL https://github.com/dalodev/wake-dist/releases/latest/download/install.sh | sh -s -- --domain wake.example.com

The server then uses https://wake.example.com as its address, with secure cookies, and evidence addresses start with https://s3.wake.example.com/. Every response of the app's address carries Strict-Transport-Security: max-age=31536000, so browsers then use only HTTPS for it; local mode serves plain HTTP and never sends it.

Your first account ​

An address on the internet can be reached by anyone, so a domain install closes sign-up: it writes SIGN_UP=invitation and a random SETUP_TOKEN to .env, and prints a sign-up link that carries the token once, at the end:

text
  → Open https://wake.example.com/sign-up?setup=<token> and create your account there.
    This link creates the first account and works only until that account exists.

Open it and create your account before anything else. Until you do, a sign-up without the token is refused, and so is a first account through a sign-in provider: link providers to your account afterwards. Then invite the people who should join. Lost the link? The token is the SETUP_TOKEN line of the installation's .env. See Sign-up and accounts.

A local install writes neither line: it listens only on this machine, so its sign-up stays open. An installation made by an older installer keeps its sign-up as it was; to close it, see Only by invitation.

--domain takes a DNS name without a scheme or port (http://wake.example.com and localhost:8080 exit 2), and cannot be combined with --port or --s3-port.

When the names do not resolve yet, the installer waits 120 seconds for https://wake.example.com/health, then exits 1 with a line naming DNS and ports 80 and 443. The stack keeps running and Caddy keeps trying to obtain the certificates: once DNS is right, curl -f https://wake.example.com/health answers, and wake-server status shows each service's health meanwhile.

What the installer writes ​

In the directoryContents
.envThe installation's settings and its generated secrets (the Postgres password, the storage's keys: random 256-bit values; on a domain, also SIGN_UP=invitation and the SETUP_TOKEN of the first account's link). Mode 0600; nothing prints them but the domain install's sign-up link. Keep a copy somewhere safe
compose.yamlPostgres, MinIO, the server, the web app and Caddy; only Caddy publishes ports
CaddyfileThe front door: the server's paths (/v1/, /mcp, /oauth/, /.well-known/, /health) go to the server, everything else to the web app; the storage address serves only the evidence bucket
wake-serverThe manager: see wake-server
LICENSEThe terms the installed release ships under, the Wake Free License, verified like the other files
backups/Backups of the database, the evidence files and .env, created by the first backup, upgrade or restore

Do not edit compose.yaml, Caddyfile, LICENSE or wake-server: an upgrade replaces them with the new release's copies. Your own settings go in .env, which upgrades keep; see Server environment.

Each directory is its own Docker Compose project, so two installations never share containers or volumes. To run Docker Compose commands on it yourself, run them in the directory, for example cd <your installation directory> and then docker compose logs server.

Run wake-server as the user who installed Wake, never with sudo: the directory is readable only by that user (mode 0700), and the daily upgrade lives in that user's crontab.

When the images cannot be pulled or the stack does not become healthy, the installer removes what it started and wrote; only a stack that is healthy but not yet reachable at its address keeps running, as above.

Run it again ​

Running the installer on a directory that already holds an installation changes nothing in it (no file, container, secret or daily-upgrade setting) and prints Wake <version> is already installed in <dir>; nothing in it changes. It adds the wake-server command and the CLI when they are missing, and names wake-server upgrade when its release is newer. --port, --s3-port and --domain apply only to a new installation.

Hardened services ​

The server and the web app run with a read-only root file system, no capabilities and no-new-privileges, as users other than root. The server reaches evidence storage as its own storage user, wake-server, which can only read, write, list and delete the objects of the wake-evidence bucket, never with the storage's root keys. Every service keeps its Docker logs in at most five files of 10 MB, so one installation's container logs stay under about 300 MB; see Logs.
